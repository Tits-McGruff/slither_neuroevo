**Low, confirmed maintenance limitation — broad parent imports conceal helper dependencies.** Examples: [publication buffers](../native/src/engine/state/publication_buffers.rs:3), [restore policy](../native/src/engine/fresh_run/restore_policy.rs:3), and [checkpoint facade](../native/src/engine/checkpoint.rs:1423). Most native children use `super::*`, and several facades use child globs. This is legal, and these children intentionally implement their parent owner. It is not a runtime circular initialization problem. However, the metric “one import prefix” is not evidence of one actual dependency or independent layering. The implementation report acknowledges this at `docs/modularization.md:201`. Optional improvement: narrow imports when touching a helper, where that materially clarifies its dependencies; no broad cleanup is required for acceptance.

**Low, plausible future regression risk — live browser ports are a continuing invariant.** [Graph view composition](../src/main.ts:1703), [graph settings port](../src/main.ts:2838), and [cached camera port](../src/main.ts:2886) correctly use live accessors for mutable/reassigned state. Replacing them with copied values later could produce stale event handlers or frames. No stale copy was found in this implementation. The added graph replacement test protects one important case, not every retained listener. Optional future tests should target a concrete stale-handler failure when those ports change, rather than adding a new generalized context/testing framework.

**Stylistic observations, not defects:** some extracted TypeScript has uneven indentation, compressed import lists, repetitive forwarding names/comments, and trailing whitespace. `git diff --check 14264e4 HEAD` reports whitespace in TSV empty trailing fields, `managed_files.ts`, and moved camera/frame comments. TypeScript and ESLint accept the code. None affects behavior, and none justifies another modularization packet.

## Physical architecture and completeness

The physical hierarchy is real: native owner subdirectories contain private specialist `.rs` files and separate test roots; browser and persistence helpers are actual `.ts` files; PyRL has two package modules. This is not a rename of large inline modules with unchanged physical navigation.

State contracts/errors, validation, memory and publication support have coherent responsibilities. Checkpoint byte codecs, numeric sources/roles, manifest validation, managed weights/restore and strict container scans are sensibly separated. Native tasks/wire shapes are separated without scattering lifecycle admission. Browser dependencies point toward graph/protocol/configuration contracts and specialist helpers. Persistence readers depend on the supplied DB and contracts, with no import back into the worker/client. PyRL rollout math depends on the existing transition/config contracts; neither new module imports the learner or starts work. No newly introduced TypeScript/Python import cycle, duplicate implementation or additional authority owner was found.

Rust children deliberately depend on parent-owned contracts through `super::*`. This is implementation-submodule coupling, not fully independent subsystem architecture. Private child declarations and `pub(super)` access mostly contain the visibility increase within the owner subtree. Existing public/crate facade paths are re-exported rather than replaced by public internal module trees. The small buffer helper and diagnostics files represent identifiable invariants; they are not arbitrary line-count fragmentation.

Browser forwarding wrappers are numerous, but preserve root access to live session state and existing handler names without giving every leaf a giant application object. The cached camera port avoids the hot-path allocation concern. Renaming the doubled camera delegation aliases would improve readability only. Persistence has one additional short current-boundary wrapper for a transactional dependency; it is justified.
